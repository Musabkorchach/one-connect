# Testnet data migration proposal

This is a review plan. Production starts with its own empty database and can be evaluated independently of any import. This review used the repository schema and route handlers. No database was queried, so eligible counts and actual ownership coverage are unknown.

## Eligibility

| Data | Eligible when | Defer or exclude |
| --- | --- | --- |
| Direct chats (`messages`) | Both participants have approved account mappings and the thread can be tied to their historical identities. Preserve message IDs, chronology, read state and per-user deletions. Recompute conversation IDs using the Production account IDs, and remap replies and attachment references. | Defer a thread with an unresolved participant or ambiguous history. Preserve deletion semantics and never restore deleted content. |
| Groups and memberships (`chat_groups`, `group_messages`) | The owner and each participant whose access or content is being copied are mapped. Preserve group and message IDs, owner and member roles, join boundaries, moderation, and read and deletion state. Preserve history only when the target enforces the same audience. | Defer a group when its ownership or access cannot be reconstructed. Leave pending invitations in Testnet and recreate them in Production if needed. Historical senders and removed members do not gain access. |
| Media (`chat_images`, `chat_attachments`, `group_media`, `email_attachments`) | The owning message or draft is eligible and the relevant route supports the media. Copy only referenced GridFS files and chunks. Preserve file IDs where possible, verify length and SHA-256, rewrite account metadata and attachment URLs, and check authorization through the Production download route. | Defer missing or mismatched blobs and ambiguous owners. Exclude orphan uploads and any media whose original visibility cannot be enforced. |
| Contacts (`contacts`, `app_state` contact data) | The list owner is mapped. Preserve the owner's labels and notes and resolve linked Pi users through mapped account IDs. Plain address-book entries may remain private text if the target format supports it. | Defer unresolved linked contacts. A stored username does not create a new contact relationship. |
| Internal mail (`emails`) | Both participants are mapped and the mail is demonstrably internal. Preserve mailbox-specific copies and IDs, direction, timestamps, read and deleted state. Reconcile sender and recipient copies using a stable source relationship where available. | Exclude inbound and outbound external mail. Defer messages with unresolved participants or indistinguishable provenance. |
| Invoice drafts (`app_state`, key `connect.invoice-drafts`) | The owner and each required linked reference are mapped. Preserve draft IDs and editable contents, rewrite `createdByUserId` using the target `privateDataOwnerKey`, and validate against the Production draft schema. | Exclude payment and settlement records, payment identifiers and executable payment links. Defer drafts that cannot be represented as inert drafts or contain unresolved required account references. |

Use account-scoped Production schemas and authorization rules as the target. If a source snapshot contains account-scoped records too, inventory both schemas and reconcile their source IDs and verified ownership before counting or importing them. Preserve source document IDs and BSON types where compatible. Record explicit source-to-target IDs for collisions and derived keys. Rewrite references consistently or defer the dependency set. Never overwrite an unrelated Production object or replace an existing user's contact list or draft state.

## Account ownership

Use a short-lived, single-use challenge with explicit approval of the named migration on both sides. Each environment independently binds the challenge to a fresh authenticated session and a server-verified Pi UID. Record a one-to-one mapping keyed by source and target environment and account ID, with verification time and consent scope. Reject expired, replayed, deleted, conflicting or reassigned links. The mapping ledger contains identifiers and evidence references only. Keep it access-restricted and out of app responses.

Pi documents verification of UID with `/v2/me`. Its public response does not document an app-record or audience field. Separate app sessions and a challenge help bind approvals but do not prove the Pi token's app of origin. Before importing real private data, require a trusted app-specific attestation or equivalent independently verifiable ownership evidence for both accounts. Keep real imports disabled if that evidence is unavailable. Matching display names or raw UIDs across app records does not authorize a link. See [Pi access-token documentation](https://developers.minepi.com/docs/authenticate-user/AccessToken) and [Platform API](https://developers.minepi.com/docs/api-reference/PlatformAPI).

The legacy audit flags username-based ownership, including IDs shaped like `pi_<username>`. A current login is insufficient to establish historical ownership of those rows. Require trustworthy historical UID-to-row evidence as well as dual account approval, or defer the affected rows. The repository audit is a starting point for a local snapshot, and requires additional coverage for target-specific fields and relationships.

## Rehearsal, approval and rollback

1. Define an explicit collection and field allowlist. Take an approved, encrypted, consistency-point source data backup including the required file/chunk pairs and an encrypted pre-import target backup. Record cutoff, schema, counts and checksums, test restore, and limit access and retention. Keep both out of live routing. Never copy sessions, login tokens, signing keys, settings secrets, Testnet subscription permissions, payments, PSTN or external mail data into the import. Redact personal content and credentials from reports.
2. Rehearse first with synthetic accounts, then with an approved read-only source snapshot restored locally and a disposable, isolated Production-schema target. Keep outbound notifications, sockets to real clients, payments and billing disabled. Produce counts by eligibility and reason, unresolved references, collisions and media hashes. Scope shared records to approved participants and defer objects if permissions would broaden.
3. Load eligible rows into staging in dependency order with a versioned batch manifest and a unique key on source environment, collection and source ID. Record the target ID and source checksum. Preserve creation dates and map account-derived IDs explicitly. An identical retry skips completed items; a changed payload or target revision becomes a conflict for review. Commit related records together where possible. Publish media references only after complete files and chunks have been verified. Keep staged records inaccessible until checks pass.
4. Reconcile counts by type and disposition, compare relationship graphs and verify file hashes. Test authorized and unauthorized access via HTTP and Socket.IO, including former members, unlinked users, deleted records, cross-environment sessions, attachment URLs, and invoice ownership. Re-run the same import and interrupt/resume a batch to verify duplicate prevention. Restore the target backup in rehearsal and confirm pre-import state.
5. Review the report and approve scope before any real run. Choose an agreed source cutoff and a write gate for affected target records while publishing. Save before-images or revision checks for any approved merges. If validation fails, hide the batch and remove only its inserted records and blobs, restoring changed rows only when their revisions still match. Preserve later native Production writes. Use full target restore only during a controlled window where those writes can be preserved or replayed. Testnet remains the source and requires no rollback.
